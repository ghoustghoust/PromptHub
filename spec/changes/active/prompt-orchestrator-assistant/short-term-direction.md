# prompt/new 整合：需求、因果与后续任务总纲

## Product

Desktop

## 文档地位与解决标记

本文是 prompt/new 整合与提示词编排助手后续工作的唯一任务总纲，保留原始需求、真实判断、因果关系、优先级和解决状态。
权威需求仍由 design.md 持有，实施索引仍由 implementation.md 第 5 节持有；本文不列接口层、代码路径或技术修改细节，具体修复以 Git 历史为准。

状态规则：

- “待解决”表示需求明确，但仍需实现、验证或取得数据授权。
- “进行中”表示已有本轮改动，尚不能视为完成。
- “已解决｜YYYY-MM-DD”只用于相关行为验证通过、必要实测完成且对应提交已经推送的问题。
- 涉及检索、调度、生成、润色、逆推或模型适配的问题，解决前必须使用 5 个全新复杂提示词逐一实测。五次结果都要检查约束、过程、输出和失败状态，不能只确认请求成功。
- 界面、存储或文档问题使用相应的真实窗口、隔离数据或文档检查，不用无关的模型测试代替。
- 五次实测只证明所示范围内的行为，不外推为普遍质量。提示词质量、生图效果和性能提升仍需用户验收与对照实验。
- 解决后只在本文简要补充解决结果、日期与剩余边界，技术细节交给 Git 记录。

## 一、原始需求与不可丢失的边界

### 1.1 真正目标

目标不是把 prompt/new 全量搬进应用，而是判断其中每份资料应当如何服务现有提示词创作：

- 可复用提示词与系统提示词进入现有 Prompt 管理和版本体系。
- 模型原生输出规则进入对应模型适配，不与普通系统提示词双份常驻。
- Skill 按实际职责成为执行契约、流程方案、方法知识或参考来源，不按文件类型一锅导入。
- 方法知识进入知识库，可执行表达进入词库，视觉参考进入参考库，具体图片素材进入共享图库。
- 大纲、剧本、分镜和生成单元成为可编辑、可保存、可版本化、具有依赖关系的文本产物。
- 所有能力最终服务稳定、高质量地产出提示词，而不是追求资源数量或工具数量。

### 1.2 产品与运行边界

- 管理上集中在提示词助手，不另建与提示词助手并列的剧本平台或素材平台。
- 集中管理不等于所有资源、按钮和步骤同屏，也不等于所有内容每轮常驻。
- 提示词助手只产出文本并保存工作区，不生图、不生视频、不自动操作 ComfyUI。
- 当前只服务 MOSS、Krea 2、MiniMax H3、Qwen-Image 2.1，其他模型资料不反向扩张范围。
- Qwen-Image 2.1 首批优先首帧与改图，不另造与现有文本任务重复的模式。
- 不执行资料包脚本，不接 ComfyUI 节点或工作流，不新增供应商、端口或第二套模型配置。
- 成人分支必须保留，既有 NSFW 知识、词条、提示词与原始级别不能因整合减少。
- 保留既有模块身份、色卡记录身份、用户选择和原始文件；正式数据迁移必须另行授权并备份。
- 已开发内容可以保留、改造或撤回，但不能因为已经写成就继续堆叠，也不能因界面错误删除底层能力和用户数据。

## 二、没有代码与接口索引的真实完成度

### 2.1 已经形成的能力

- 已有“意图驱动 · 自动编排”和“词条驱动 · 人工定稿”两种引导方式。
- 人工选材具有锁定、推荐、参考、排除四种状态，并有结果回填和持久化。
- 图片任务已有扩写、专业编排、润色、反推、编辑和受控随机；视频任务已有 H3 的多种文本任务入口。
- 已有规则卡、写作层、知识包与契约、色卡参考、布局画布、预算、结果对照、溯源、保存、流式和取消。
- 已有确定性的输入分类：命名身份、触发词、固定参数和描述文本可以走不同路径，纯身份输入可以不检索。
- 已有精准解析、短语与词法召回、聚焦与探索深度、候选排序、冲突过滤、分类禁查和调用上限。
- 已有两条真实检索链：动态润色检索链与通用工具检索链。
- 已有候选级评测脚本，可以检查精确表达、中英文片段、无匹配、禁查、去重、领域和预算等边界。
- 色卡已有稳定记录身份与联合索引基础；014 四库已有只读导入、查询和存储基础。
- 生图批次已经具备记录来源 Prompt、Prompt 版本、实际提示词、模型、参数和参考图的基础。

### 2.2 只能算部分完成的能力

- 两条检索链都由模型参与查询决策，也仍由模型生成最终提示词，不是“模型只调度、脚本负责最终产出”。
- 当前溯源能显示决策摘要、轮次、查询数、候选数和资源来源，但不能完整还原每轮查询、候选、过滤、采用和降级过程。
- 知识模块与色卡可以证明“注入过”，不能仅凭现有摘要证明它们实际影响了哪一句。
- 模型给出的采用理由属于模型自述，不等于可验证的事实或因果关系。
- 词库召回评测不等于最终提示词质量，更不等于生图效果。91K 数据的实体命中率、真实本地模型稳定性和下游收益仍需实测。
- 生图批次快照尚未与编排运行、调度规则版本和完整生成环境形成同一条证据链。
- 共享色卡已有联合索引与单缩略图能力，完整多剧照和展示资产并集仍未完成。
- 图库底层能力已存在，但曾实现的界面只有全局勾选和数量，没有明确使用目标与运行结果，因此已撤回。

### 2.3 尚未完成或不能宣称完成的事项

- 模型只负责处理与调度、确定性脚本负责所有最终文本的完整工作链尚未实现。
- 剧本主导 Skill 的单选互斥尚未实现；当前多个选中包的契约可能叠加。
- 统一的任务合同、执行记录、最终编译和下游实验闭环尚未形成。
- 尚未证明 32K 本地模型在现有资源规模下能够稳定调度，也不能把未超上下文等同于生成质量良好。
- 尚未完成 MOSS 逆推、新逆推、扩写、润色、知识与色卡之间的系统 A/B 验证。
- 尚未完成剧本到分镜再到 H3 生成单元的可交互流程样板。
- 尚未完成 Qwen 首帧/改图适配和真实单单元闭环。
- 历史重复色卡、旧参考角色和旧 contract 的正式数据迁移没有授权，也没有完成。

## 三、核心因果：为什么中间层必须先于新功能

### 3.1 资源规模与模型能力不是同一件事

系统可以管理大量资源，但模型每轮只能看到少量相关内容：

资源可管理
→ 当前任务决定可访问范围
→ 确定性规则筛选候选
→ 当前步骤选择必要内容
→ 形成精简工作单
→ 模型处理或写作
→ 校验并保存结果

如果把“资源存在”直接变成“工具全部开放”，后续链条会变成：

权限过多
→ 工具描述与候选增加
→ 模型难以决定调用什么
→ 调用轮次与历史增加
→ 上下文变长、速度下降
→ 关键要求被稀释
→ 输出更不稳定，甚至无法完成

32K 是容量上限，不是稳定工作目标。质量问题可能先于硬超限出现，预算阻断只能是最后保险，不能替代调度策略。

### 3.2 为什么输出结果不能反推过程

内容少时，用户还能从结果大致判断是否调用了正确资源；内容多时，最终文本无法说明：

- 查询是否准确；
- 是否漏掉了更合适的候选；
- 是否错误加入了无关知识；
- 是否发生了降级；
- 固定要求是否在中间步骤被覆盖；
- 色卡或知识是实际生效还是仅仅出现。

因此过程可见必须是产品能力，而不是开发者调试信息。可见的是结构化动作和证据，不是模型隐式思考过程。

### 3.3 为什么生图结果不能直接归因

下游结果同时受底模、LoRA、提示词、采样器、步数、CFG、分辨率、seed、工作流和二次润色影响。

单张好图或坏图不能证明某一项是原因。只有保存实际提示词与完整生成环境，并在固定其他条件时逐项对照，才能判断问题更可能来自哪里。

中间层可以提供关联证据，但不能自动宣判因果。

## 四、统一中间层的真实需求

中间层不是再写一个大脚本，而是五个互相依赖的职责。

### 4.1 任务合同

在模型调用前，由用户与系统确定：

- 当前任务、步骤和目标模型；
- 人工或模型引导方式；
- 固定事实、禁止修改项与内容范围；
- 当前主导 Skill；
- 允许访问的资源类型；
- 是否允许创作新内容；
- 当前预算和依赖状态。

模型不能自行扩大权限。

### 4.2 确定性调度策略

访问规则应集中、可解释、可复用：

- 命名身份、LoRA 触发词和固定参数走精准解析，不做模糊扩展。
- 明确描述走短语或聚焦召回。
- 只有允许创意补充的槽位才走探索召回。
- 逆推以图片为事实来源，只接受等价表达，不自由补充视觉事实。
- 剧本流程只启用一个主导 Skill，按当前步骤提供必要契约。
- 知识按任务和步骤选择模块，不整包常驻。
- 色卡与图库只取当前明确选择的内容，不开放整库漫游。
- 模型可以提出调度请求，系统必须能拒绝、限制或要求补充。

### 4.3 执行记录

每次运行都应能还原：

- 使用了哪份任务合同和哪版调度规则；
- 动作由用户、模型还是确定性策略发起；
- 查询内容、类型、目的和深度；
- 候选、匹配关系、过滤原因与预算；
- 采用、调整、创造、弃用及对应输出片段；
- 实际注入内容与 token；
- 工具失败、路径切换、降级和警告；
- 最终 Prompt 版本与内容身份。

观察事实、模型自述理由和下游效果推测必须分开。

### 4.4 最终编译

“模型只调度而不生成”只适用于能够确定性组装的范围：

- 身份、参数、LoRA 和固定约束；
- 已选词条与参考；
- MOSS Layout；
- H3 结构化生成单元；
- 有明确模板和语法的目标输出。

剧本、创意扩写和自然语言润色若完全禁止模型写作，就只能依赖模板和既有表达组合，不能同时要求自由创造新内容。

因此采用的工作判断是：

- 默认调度型：模型输出结构化决策，系统组装最终结果。
- 显式写作型：确实需要创意时，明确允许模型写某些槽位，系统再校验、记录和编译。

这是一种内部执行策略，不是取代人工/模型双模式的第三种用户模式。

### 4.5 下游实验与归因

应把编排运行、Prompt 版本、实际提示词、底模、LoRA 及权重、采样参数、分辨率、seed、工作流版本、参考图和输出评价关联起来。

有效判断顺序是：

1. 同一设置比较原始提示词与编排提示词。
2. 同一提示词使用多个 seed，先判断自然波动。
3. 固定其他条件，只改变 LoRA、步数、分辨率或工作流中的一项。
4. 再判断问题更可能来自哪一层。

## 五、既有双模式、任务结构与剧本职责

### 5.1 不重新发明双模式

已有双模式就是：

- 意图驱动：模型主导编排。
- 词条驱动：人工选材定稿。

生成与保存是同一创作闭环的两个动作，不构成另一套双模式。

单条创作与流程创作是任务结构，不是第三种引导模式。普通扩写、润色、反推和编辑通常一步完成；只有确实存在中间产物与依赖时，才展开流程。

调度型与写作型是内部执行策略，也不替代上述双模式。

### 5.2 剧本不是普通提示词模板

剧本既有线性内容结构、时序、角色和连续性，也有大纲、正文、分镜等创作依赖。

统领型剧本 Skill 往往各自规定互斥的结构、步骤与输出要求：

- 同一流程只能有一个主导剧本 Skill。
- 不同步骤的专用 Skill 只有职责不重叠、依赖明确时才可组合。
- 方法知识可以多选，但受适用范围与预算控制。
- 不做多个主导 Skill 的自动合并。
- “整包逻辑生效”不等于“整包全文常驻”。必须全文硬塞才能运行的 Skill，应转化为应用原生流程。

### 5.3 共享创作语义与模型末端适配

生图与视频可以共享：

- 主体、动作、场景、服装与姿势；
- 构图、镜头、光线、色调；
- 人物一致性、动作结果与连续性；
- 剧本、分镜和首尾帧的组织方法。

模型末端分别处理：

- Caption、Tags、Layout 等输出形式；
- H3 的时长、生成单元和参考输入要求；
- Qwen 的首帧、改图和结构要求；
- 各模型不能共享的硬限制。

共用规则不能重复塞入每个模型规则卡，也不能把 H3 的输出格式冒充通用格式。

## 六、资料进入系统的正确位置

### 6.1 提示词与系统提示词

用户可复用的提示词和系统提示词进入现有 Prompt 管理与版本体系，保留用途、正文与来源。

模型原生规则若已成为适配依据，不再作为另一份普通系统提示词重复生效。

### 6.2 Skill

按作用判断，而不是按文件夹或扩展名判断：

- 输出语法进入模型规则。
- 当前步骤的执行、确认和输出要求保留为步骤契约。
- 可复用方法进入知识库。
- 视觉参考进入参考库。
- 多步产物的先后、输入与确认点转化为流程方案。
- 自动脚本和外部工作流不执行，由应用自身的保存、版本与界面能力替代。

大纲级 Skill 可以统领流程，但不能因为内容全面就每轮全文注入。

### 6.3 知识库、词库与图库

三者回答的问题不同：

- 知识库：为什么、什么时候、怎么做。
- 词库：提示词里可以写什么。
- 图库：具体选哪一个、看起来是什么。

图库不需要也不应该完整摘进知识库。只抽取方法性文字进入知识库，经审核的可执行文本进入词库；图片、分组、视角和来源关系留在图库。

知识模块可以软引用示例图，同一素材可以经审核投影为词条，但来源保持同一个，不重复导入、不重复注入。

图库属于参考库中的具体素材部分：色卡是风格参考，服装、发型、人像和姿势是实体与动作参考，不新增第六个资源层。

### 6.4 镜头

景别、运镜动机、轴线、构图、连续性和首尾帧组织方法属于可选知识。

可执行的镜头术语与中英表达进入现有镜头词条。模型能否接受某种结构、时长或输入方式仍由目标模型规则决定。

姿势素材的观察角度只是素材属性，不能自动当成运镜指令。

### 6.5 成人内容

成人内容是任务的内容范围，不是新模型模式。

开启范围只表示允许选择相符资源，不代表每轮强制成人内容，也不代表全部成人资料整包注入。MOSS、Krea 2、MiniMax H3、Qwen-Image 2.1 均保留成人适配路径。

## 七、色卡的互补合并判断

旧、新色卡不是两个应当互相替代的产品。静态盘点已经表明：两边都有完整的 200 个导演身份，正文实质内容没有差异，但 JSON 表达、图片与展示资产存在互补关系。

准确结论是：

- 不是文件完全重叠，而是导演身份与正文高度重叠、资产可以互补。
- 按导演数字身份形成一个逻辑记录，不重复导入正文，不建立第三份重复目录。
- 一个来源提供主正文与主元数据，另一个来源补充独有图片和展示资产。
- 同源重导入保留记录身份和用户已有选择。
- 每轮最多选择三张色卡，三张是并列视觉参考，没有先后顺序，也不构成因果关系。
- 色卡只影响色调、光线和构图方向，不替代模型规则，不堆导演姓名，不把整库图片送入模型。
- 多剧照与完整展示资产并集尚未完成，不能宣称合并任务已经全部结束。
- 历史重复记录只做只读盘点和显式映射方案；未经授权不删除、不迁移、不用重导清库。

## 八、014 图库的真实定位

首批只接服装、发型、人像、姿势四个有明确索引的库，共 5,238 条：

- 服装 1,407 条；
- 发型 893 条；
- 人像 1,499 条；
- 姿势 1,439 条。

图片保留在本机只读来源，索引保存分类、标签、分组、视角和来源关系。“自定义”目录缺少可靠清单，继续跳过。图片及原始数据不默认进入仓库、安装包、导出或云同步。

图库应当是 PromptHub 完整的共享功能，支持浏览、筛选、详情和明确目标的使用，不是 H3 的附属品。

需要撤回的不是图库，而是“只保存勾选数量、没有实际结果”的交互：

- 普通提示词创作中，选择素材可以将审核后的文本加入当前选材台，默认推荐，可以再锁定。
- 人工驱动中，素材选择遵守现有四态。
- 模型驱动中，用户显式选择成为用户约束，不能被自动检索覆盖。
- Qwen/H3 视觉参考中，素材绑定到指定角色或生成单元，需要读图时才使用相关图片。
- 知识示例只解释方法，不自动变成提示词正文。

角色素材槽位的单选、多选与姿势组规则，在角色绑定设计时单独验收；当前不提前实现。

服装英文短语等真实文本只有经过翻译预检和用户验收后才投影为词条，不能按图片数量重复造词。

## 九、流程创作的因果链

推荐共享创作链：

原始意图或已有文本
→ 必要的大纲或剧本
→ 可审阅的分镜
→ 当前生成单元的事实与素材准备
→ 目标模型适配
→ 文本成稿
→ 保存与版本
→ 用户验收或回填真实图片

每一步只消费当前步骤所需规则、知识、输入和必要相邻状态。上游修改只标记下游需要重审，不自动批量重跑。

用户可以从已有剧本或分镜进入，不强制从小说或大纲开始。

H3 以不超过 15 秒的生成单元组织输出。15 秒是上限，不是机械切镜间隔；一个单元可以包含多个镜头，按动作与节拍决定边界。

多参考、首尾帧和混合输入共享准备逻辑，但分别适配目标模型。依赖真实图片的成稿必须等待用户回填，不能伪造已上传素材，也不能把素材数量当成依赖完成。

## 十、统一操作逻辑

### 10.1 资源导入

导入是资源管理动作，不是本轮生成动作。

用户先选择资源类型，再选择来源。应用识别目录结构，说明读取范围、跳过原因和导入后的用途，预览确认后才写入索引。

色卡的互补来源可以联合预览；014 一次处理一个明确图库根目录，不提供无效的多目录选择。

### 10.2 本轮参考

色卡多选最多三张、并列生效。查看详情与改变选择是两个明确动作，已选清单、剩余名额和实际作用始终可见。

### 10.3 图库使用

允许全局浏览与筛选，但不允许无目标勾选。

每个使用动作都必须说明用于哪个草稿、角色、生成单元或知识示例，以及实际产生的是词条候选、文本参考还是视觉素材。

### 10.4 运行前、运行中与运行后

- 运行前：显示当前任务、主导 Skill、允许资源、固定要求和预算。
- 运行中：显示真实阶段、实际检索与失败状态，不显示伪造百分比。
- 运行后：显示文本差异、资源证据、采用与弃用、降级、警告和最终结果。
- 下游使用后：能够追溯实际 Prompt 版本与生成环境，而不是只看一张结果图。

工具路径降级修复（2026-11-26）：

- 根因不是随机波动：输出 schema 没有列出决策字段，工具合同却要求返回它，解析又把这个字段的缺失

  更容易截断，32K 是“检索 + 长答案”的实际前提。

完成判定：
