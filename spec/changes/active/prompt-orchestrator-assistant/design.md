# 提示词编排助手（PromptHub 内置能力）

## Product

Desktop

## 状态

review-pending — 第一版已实现并做针对性真实验证；第四轮原生 MOSS 布局画布已实现并验证，词条选材、风格/主题包和参考数据导入仍待实施与评审。

## 目的与定位

PromptHub 从"提示词管理工具"扩展为**知识驱动的提示词编排系统**。用户可以只给出
一句话意图，也可以主动挑选词条与预设；系统结合目标任务、规则卡片、风格/主题包
与创作偏好，从结构化词库精确选材，按视觉逻辑组织成更易被图像或视频模型正确执行
的提示词。底模与 LoRA 的搭配统计不属于当前范围，LoRA 仅在确有专用激活词时提供
可选约束。

**不是 RAG**：任务不是从文档找答案，而是选对元素并按目标组织。RAG 作为可插拔
后期模块，只承载社区经验、模型说明这类不适合拆成原子词条的内容。

**不做外挂**：不是独立 HTML 工具、不是本地插件、不是外部端口服务。是 PromptHub
自身的一等功能，落在既有包边界内：

- `packages/db`：结构化词库（已完成）
- `packages/core`：编排逻辑、技能规则、LLM 端口
- `apps/desktop`：IPC 入口与能力面板
- Skill 生成器：产出可复用的提示词技能，本地模型有参考但保留创造性

## 本地模型基线（2026-11-17 实测）

### 环境

- GPU：NVIDIA GeForce RTX 5060 Ti，8151 MiB 显存
- 内存：31.6 GB
- 引擎：llama.cpp build 12445（CUDA 13.5），`/d/tools/llama.cpp/llama-server.exe`
- 模型：`Qwen3.5-9B-The-Defiant-Fable-Uncnr-Heretic-NEO-MAX-IQ4_XS.gguf`
  （6.0 GB，**非 MTP 版**，见下节关键结论）
- 多模态：`...-MTP.mmproj-f16.gguf`（876 MB，视觉投影，尚未接入验证）
- 同机运行 ComfyUI（`krea2_image2.1_moss_minimax`），显存共享

### 速度实测（配置对照）

| 模型文件 | 配置 | 显存 | 生成速度 |
| --- | --- | --- | --- |
| MTP-IQ4_XS（6.1 GB） | ngl 99 / ctx 8192 / MTP 开 | 7680 MiB | 4.69 tok/s |
| MTP-IQ4_XS（6.1 GB） | ngl 99 / ctx 4096 / MTP 开 | 7631 MiB | 5.52 tok/s |
| MTP-IQ4_XS（6.1 GB） | ngl 28 / ctx 2048 / MTP 开 | 7630 MiB | 4.60 tok/s |
| MTP-IQ4_XS（6.1 GB） | ngl 99 / ctx 2048 / MTP 关 | 7630 MiB | 5.33 tok/s |
| **IQ4_XS（6.0 GB，非 MTP）** | **ngl 99 / ctx 4096 / 无投机** | **7355 MiB** | **60.09 tok/s** |

结论：

- **必须使用非 MTP 版本模型文件。** 同为 IQ4_XS 量化、同一引擎与硬件，
  MTP 变体只有 4.6–5.5 tok/s，标准版 60 tok/s，**相差约 11 倍**。
  MTP 变体多出的 `blk.32.nextn.*` 层被 llama.cpp 判为 unused 丢弃，但该文件
  在标准解码路径上无法获得有效 offload。带 `-MTP-` 的权重文件不要用于常规生成。
- 配置微调（层数、上下文、KV 量化、投机解码）对该差异无补偿作用，全部无效。
- 速度基线应记为 **约 60 tok/s**，早期 5 tok/s 的记录源于选错模型文件，已作废。
- 单次结构化编排实测：94 token / 2.1 秒 / 57.47 tok/s，交互完全可用。

### 关键运行约束

1. **必须关闭 thinking**：Qwen3.5 默认进入推理模式，`content` 返回空、
   内容全在 `reasoning_content`，80 token 全部消耗在思考链上。启动需 `-rea off`
   （或请求侧 `--reasoning-budget 0`）。
2. **与 ComfyUI 共享 8 GB 显存**：纯文本常驻约 7.3 GB，加载视觉投影后约 7.7 GB。
   生图前需卸载模型、生成后重载。该切换是必要项而非优化项。
3. **OpenAI 兼容端点可用**：`http://127.0.0.1:8080/v1/chat/completions`，
   PromptHub 无需理解 GGUF，按既有 openai 协议接入即可。
4. **视觉请求必须预留上下文**：单图默认占约 3800 token，`-c 4096` 时输出仅剩
   200 余 token，会在 `finish_reason: length` 处静默截断。识图场景 ctx 取 8192，
   并用 `--image-max-tokens 2048` 控制图片开销。

### 提示词遵从性验证

输入"东方女子倚在闺房窗边，黄昏，古典唯美写真"，要求输出结构化 JSON 并区分
fixed / flexible / optional 三层：

- 格式遵从：输出为纯净 JSON，无 Markdown 围栏、无前言、无解释。
- 分层正确：`fixed` 全部为用户明说元素；`flexible` 为黄昏光层次与空间关系
  推导；`optional` 为茶具蒸汽、钟声倒影等创意补充。
- 质量词抑制：未出现 masterpiece / 8k / ultra detailed 等无效词。
- 代价：94 token 耗时 2.1 秒（57.47 tok/s）。

**结论：模型完全可用。格式遵从、三层分层、质量词抑制三项均通过，单次编排
2–3 秒，可作为 PromptHub 的实时编排引擎，不需要为速度做交互降级。**

`mmproj-f16` 视觉投影加载成功（`loaded multimodal model`），显存增加约 363 MiB。

识别结果与图片实际内容逐项一致：

- 服装：绿色水手领校服、白色条纹、大号黑蝴蝶结、米色格纹开衫
- 面部：琥珀色眼睛、泛红脸颊、嘴唇微张
- 动作：右手握住一缕发辫
- 场景与光照：虚化欧式街道、秋日树木、行人、明亮日光
- 风格：anime illustration

**关键可靠性证据**：模型主动输出 `not_visible: ["legs","feet","lower body"]`，
未对半身构图之外的部位编造内容。

图片 token 与质量的权衡（同一图片、同一提示词）：

| `--image-max-tokens` | prompt tokens | 总耗时 | 细节保留 |
| --- | --- | --- | --- |
| 默认（未限制） | 3799 | 约 80 秒 | 完整，含汗珠、手握发辫 |
| 1024 | 1223 | 约 24 秒 | 漏汗珠与手握发辫 |
| **2048（推荐）** | **2224** | **约 36 秒** | **含手握发辫、脸红、唇微张、黄格纹，仅漏汗珠** |

结论：识图逆推可用且不发散。**生产配置取 `--image-max-tokens 2048`**——
36 秒、细节接近完整，是速度与精度的最佳平衡点。1024 可作快速预览档。

## 第一版范围

不做 RAG、不建向量索引、不自动操作 ComfyUI（人工确认后执行）。

按顺序推进：

1. **词库维度补齐**（`packages/db`）：`series` 系列维度与长句模板位。
   现有 schema 只有 `en`/`zh` 两个短文本位，装不下社区词库的长句片段。
2. **编排层**（`packages/core`）：意图解析 → 词库选词（过滤适用模型、排除互斥）
   → 技能规则 → LLM 组合 → 三层输出（初始版／完整改造／分层字段）。
3. **任务、输出与适配分离**：扩写／专业／润色／反推／编辑／受控随机是任务；
   JSON 是输出结构，LoRA 是适配约束，都不再冒充普通任务模式。受控随机 = 先定场景
   约束再在范围内随机；底模/LoRA 搭配统计与自动注入模型 ID 不在当前范围。
4. **IPC 入口**（`apps/desktop`）：先可测命令，面板随后。
5. **Skill 生成器**：以词库与技能规则为参考，生成可复用的提示词技能文件，
   保留模型创造性，产出需标明哪些是参考、哪些是建议。
6. **本地模型设置与引擎控制**（用户后续明确要求）：设置内新增本地模型板块，
   管理 llama.cpp/GGUF/mmproj、推理参数、健康状态和自有进程启停；启动后连接现有
   AI 模型设置。编排工作台只提供状态、启动/停止和设置快捷入口。ComfyUI 的自动
   显存交接仍不在本轮范围。

## 第二轮：输入结构、官方规则与引导方式（2026-11-18）

用户实测反馈后，原生界面不再把八种模式视为同一输入，也不再继续平铺旧 `json/lora` 任务：

- 图片任务为扩写、专业编排、润色、反推、编辑、受控随机；JSON 改为可选结构化载荷，
  LoRA 改为高级适配约束。旧 CLI 的 `json/lora` 仍保留兼容，不用于新版界面分类。
- 反推支持文件选择、剪贴板粘贴和拖放；不同任务显示不同输入。每个任务旁直接展示
  用途、所需输入和输出，不要求用户猜测八种模式的关系。
- 引导方式分为 意图驱动 · 自动编排与词条驱动 · 人工定稿。词条驱动 · 人工定稿在右侧提供大面积词条选材
  搜索、分类筛选和显式锁定区，用户再补充一点想法，Agent 只做克制润色。
- 自动词库默认每类最多 2 条、约 900 Token 上下文预算；显式词条选材始终保留，
  词条驱动 · 人工定稿默认不自动加词。词库是按需知识，不是把整库复制给本地小模型。

### 官方资料的真实边界

- `prompt/moss官方生图规范.htm`：MOSS 支持 Caption、动漫 Tags、Layout JSON。
  新增 Tags 输出；长描述用普通英文句子，精确文字保留原语言与换行。
- `prompt/krea2官方生图规范.htm`：Krea 2 支持段落或短语列表，要求一种风格/媒介，
  保留原始主体、动作、数量、颜色、位置和媒介，不添加没有暗示的人物或物体。
- `prompt/minimaxh3官方生图规范.htm`：实际是视频规范，不是静态图规范。新增
  文生视频、首尾帧、多参、图生长视频、短剧 Agent 系统 Prompt 与实验性卡点任务。
  文生/首尾帧使用三字段，多参使用六字段；短剧产出的是 Agent 系统 Prompt，不是单条视频。
- Qwen Image 2.1 经用户确认本轮不接，不把 Krea 2 错写成 Qwen，也不编造其官方规则。

### MOSS Token 软预算与实体框架

用户确认的计数单位为 Token。`50–500` 收益明显、`500–2000` 收益递减、约 `2000`
较优、约 `2500` 进入平台期属于用户实测经验，不写成官方硬限制，也不强凑长度。
扩写可以深化初始框架中的神态、发型、服装、姿势、手部动作、场景内物件、材质、
光影与构图；避免突兀加入无关人物、动物或新剧情。结果优先调用连接模型的
`/tokenize`，不可用时给出确定性估算，并始终注明不是 MOSS/MiniMax 官方分词计数。

### H3 输入与验证

- 首尾帧重在撰写中间衔接，图片是可选参考，不调用 ComfyUI，也不假装已生成视频。
- 多参支持最多 6 张参考图和逐图用途；长视频要求连续性与总时长；短剧生成系统 Prompt。
- 卡点按用户时间戳组织切镜和动作重音，但明确标为实验性、待人工验证。
- Core 新增任务级输出校验：H3 缺三字段/六字段、短剧不是多段系统 Prompt、MOSS Layout
  不符合 summary/items/bbox 契约时，不能标记为完整结果，只能显式降级。
- 真实原生 E2E 已验证：剪贴板图片进入反推、H3 三字段真实生成、词条驱动 · 人工定稿搜索并锁定
  词条选材。另一次普通句子冒充 H3 的验收暴露问题后，已通过强化契约与校验修正。

## 第三轮：真实图片输入与规则隔离修正（2026-11-18）

- 本地图片不再依赖 Electron 原生文件对话框、复制到媒体目录和读回授权链，改为
  Chromium 文件选择后直接 `FileReader`，失败不再静默。

- Token 区间只作观察指标，不用于提前结束、删减或强行凑齐。旧默认 `max_tokens=2048`
  已提高到 4096，避免 MOSS 正文加 JSON/字段后被提前截断；达到上限仍不采用半截正文。
- 选择顺序改为先选规则卡片，再显示该规则支持的任务：MiniMax-H3 只出现视频任务，
  MOSS/Krea 2 只出现图片任务。H3 不再显示 LoRA、图像系列和图片词条选材设置；
  Krea 2 只有 Caption，MOSS 保留 Caption/Tags/Layout。
- 结果区显示规则卡片与输出格式，视频结果使用“视频创意摘要 / MiniMax-H3 视频提示词”
  标题，不再与图片结果共用一套含混展示。
- 真实原生回归通过：实际 PNG 文件输入、系统剪贴板按钮粘贴、图片区 `Ctrl+V`，
  以及 MOSS Tags、Krea 2 Caption-only、H3 视频专属布局。

## 关键设计约束

- **三层创造力不可简化**：直接要求（必满足）／合理推导（可说明依据）／
  创意补充（必须标明是建议）。`moodyMossPromptWriting_v40.txt` 已内建
  FIXED / FLEXIBLE / OPTIONAL 三级标记，是该契约的既有实现，规则层不需重写，
  只需接入词库候选。
- **排序策略按模型可选**：kb.json 的 `semantic_order`（质量→画师→角色→外貌→
  服装→姿势→场景→光影→镜头）与 K2 协议要求（画风段必须最前且连续）不一致，
  不能硬编码单一顺序。
- **字段归属校验**：外观卡与写真包的既有实践已暴露真实冲突（"脚踝"属服饰而非
  标志特征；长卡只写身高体型比例，换景别才不矛盾）。词条需要分类归属约束与
  跨字段冲突检测。
- **角色档案与本次出图配置分离**：外观卡（跨场景稳定身份）对应角色档案，
  写真包（单次拍摄参数）对应本次配置，两者存储与生命周期不同。
- **验证状态不可省**：社区流传≠已验证；Krea2 有效≠MOSS 有效。词条需保留
  来源与验证状态（待整理／待验证／已验证／已弃用）。

## 对照式结果界面（2026-11-19 落地，已做真实模型复验）

- 布局由“上下堆叠”改为三栏：条件栏（规则卡/任务/模型/输出）｜工作区（输入、模式字段、词条驱动词库）｜结果栏（独立侧栏，可展开）。

- 系统提示词层：新增 `systemPromptLayer` / `systemPromptLayerSource`。可从提示词库载入已保存 prompt 的

- 存库/收藏：结果栏可“存入提示词库”，写入 `userPrompt=完整版`、`systemPrompt=系统提示词层`、
  `source=prompt-orchestrator`、`tags=[规则卡, 模式]`，并可选同时收藏；收藏走既有 `updatePrompt(isFavorite)`。

## 第四轮：词条选材工作台、风格主题包与原生海报布局（2026-11-19，布局画布已实施）

本节约束来自最新实测反馈。**原生 MOSS 布局画布已按本节后述契约落地并完成真实
Electron 验证；“选材台”已完成多字段池、多选、锁定与普通窗口适配，尚未做真实窗口
验收；风格/媒介素材包与预设组合已按现有词库落地（见下节），参考数据导入已完成，
但真实窗口的视觉验收仍未做。**

### 为什么继续开发

第一版已经证明“词库 → 规则卡片 → 本地或云端模型 → 对照结果 → 存库/收藏”的原生
链路可行，但当前词条选择密度、风格覆盖和窗口适应性仍不足：普通窗口下主按钮会被
挤成两行，词条选材区可选项有限，结果更像通用编排器而不是可精细控制的创作工作台。
下一阶段的目标不是复制一个独立提示词生成器，而是把丰富的选材、预设和布局能力
接回 PromptHub 已有的提示词库、收藏、系统提示词层与后续测试链路。

### 继承且不可回退的原则

- 所有新能力继续是 PromptHub 原生 Electron 功能，不引入独立 HTML、ComfyUI 插件、
  外挂应用或额外服务端口。
- 规则卡片决定模型语法与任务边界；风格包、主题包、词条和预设只提供创作素材，
  不得把 MOSS、Krea 2、MiniMax-H3 重新混成同一套输入和输出。
- 保留“直接要求 / 合理推导 / 创意建议”三层来源。用户显式选择的词条是直接要求，
  Agent 不得擅自替换；自动补充必须可识别、可审阅。
- Token 只作观察指标，允许合理冗余，不得为了落入区间而删减、提前结束或截断句子。
  词库上下文预算只限制注入小模型的参考资料量，不限制最终提示词长度。
- 词库是按需检索与组装的知识，不是把整库或整套模板一次性塞给模型。本地与云端
  chat 模型继续复用现有 AI 设置，不因增加选材功能而新建第二套模型配置。
- 结果继续放在右侧独立区域并保持左右句级对照；系统提示词层、存入提示词库和收藏
  是既有主链路，不能被新的选材界面削弱。

### 命名与普通窗口布局

- 界面新名称为 **“选材台”**（2026-11-19 定名，先前暂记“词条选材”），替代“词库
  预制菜”。“词条驱动 · 人工定稿”继续表示先选材、后由 Agent 克制组织与润色的工作
  方式；内部枚举和旧数据无需改名。
- “开始编排”是主操作，不得因普通窗口宽度不足而压缩成两行。待实施布局将其放在
  中间工作区底部的完整宽度主操作区，保持单行、可见且不被右侧结果栏挤压。
- 宽屏保留“条件栏｜工作区｜右侧结果栏”。普通窗口优先折叠条件栏或把结果栏改为
  可展开右侧抽屉，为选材与主按钮让位；不得简单退化为上下对照。窄窗口也须保留
  明确的左右对照查看入口。
- 选材密度提高后，分类导航、候选区和已选区应分区滚动，不能让整页随词库长度无限
  增长；主要操作与已选摘要保持可见。

### 编排主导与精确排版的兼容（2026-11-19 实施）

- “精确排版”与“词条驱动 · 人工定稿”是正交选择，不得因引导方式隐藏或挤扁画布。
- 画布在工作区中作为独立标签 **“版面画布”**，与“词条选材”并列；切换标签不丢失
  选词、框选和画布状态。
- 已锁定词条在画布标签常驻，**“写入选中框”** 把词条确定性追加到选中框描述，不依赖
  模型猜测；结果仍由 PromptHub 编译器按归一化 bbox 生成最终 Layout JSON。
- 原生布局草稿的规则卡片范围从 MOSS 扩展到 MOSS 家族（`moss`、`moodyMoss`），二者
  共用 `abs_centralized` / `yxyx` 契约；Krea 2 仍只支持 Caption。
- 布局模式下的编排门槛：画布宽高为 16 的倍数、至少一个框、文字框有精确文案、整体
  画面描述非空。未建框时不得开始编排。
- 结果栏在宽屏可拖拽调宽（440–640px），普通窗口仍使用覆盖式抽屉，二者不共享挤压
  选材台的布局。

### 本地推理引擎的手动卸载（2026-11-19 实施）

- “停止请求/暂停”不等于释放模型：llama-server 进程不退出时，权重、KV 缓存与显存
  仍然占用。界面必须提供显式的 **“卸载并释放显存”**。

### 画师词条、二级分类与风格互斥（2026-11-19 确认）

- **画师词条的生效机制有两条，不能混为一谈**：

## 第五轮：输入类型路由与实体解析（2026-11-22，core 已落地，界面待验收）

### 为什么开发

第四轮之后，词库已经能按分类精确选词，但**输入本身没有类型**：角色名、画师名、LoRA 触发词、
镜头参数和普通描述被一视同仁地交给词法检索。隔离库实测暴露三个具体问题：

- 自动选词默认包含 `artist`（`prompt-orchestrator-vocabulary.ts` 的默认类别表），提示词里
  出现 `wlop` 时会把 danbooru 画师行当“相关词条”写成字段，违反“MOSS/Krea2 不解析 `@`、
  画师不得进入自动选词文本”的既有约束。
- `character` 分类混着三类内容：真名（`raiden shogun`）、**名字+外观整串**（1,007 行，
  如 `ganyu \(genshin impact\), blue hair, ...`）和通用标签（`1girl`、`动漫角色`、`风格`）。
  只按分类取行，会把外观当身份，或把通用词当人名。
- 同一身份存在多行（`ganyu` 有 3 行、`raiden shogun` 有 2 行、`雷电将军` 跨 3 个来源），
  按文本相似度选一行等于替用户猜身份。

### 已确认的边界（2026-11-22 用户裁定）

- 命名实体走**精确/别名解析**，不做模糊、前缀或向量相似度；歧义时返回候选并标注不确定，
  **不阻塞主流程**，也不猜。
- 画师按目标管线路由：Anima 输出 `@artist`；Kaloscope 只给节点参数
  （`artist_name` / `bank=artist-v1.safetensors` / `style_guidance=6` / `adapter_strength=1`，
  底模须 MOSS-Image Base）；Krea2/H3 不写画师；**MOSS 官方支持画师标签**，因此用户显式选择的
  画师在 MOSS 下保留为不带 `@` 的普通标签，自动选词仍然禁用。
- 目标管线由新增可选输入 `targetPipeline` 声明，缺省由规则卡推导（`moss`/`moodyMoss`→moss、
  `k2`→k2、`minimaxH3`→h3），`anima`/`kaloscope` 必须显式选择。不改动 `PromptOrchestrationSkill`
  枚举与规则卡文案。
- 角色名是身份锚点：只固定名字与系列限定，**不默认加载外观**；外观只在用户明确要求时作为
  参考材料。`nsfw` 与高风险属性不自动加入。
- 别名回填先窄后宽：只覆盖通过身份判定的角色与非 danbooru 画师；59k danbooru 画师段因大量
  符号噪声（`!!`、`#b7282e`、`$hu`）暂不回填。

### 数据与契约

- 新增 `term_aliases`（`term_id`、`alias`、`alias_key`、`kind`：canonical/series_less/zh/curated、
  `origin`：derived/curated），`alias_key` 建索引；`migratePromptVocabSchema` 幂等补表，
  旧库升级不改动 `prompt_terms` 数据。
- 别名键归一化：NFKC、小写、去 `@`、去权重语法与强调括号、去转义、下划线转空格、去引号。
  一个 bundle 行同时产出“原始整串”“身份串（name + series）”“省略系列名”三种键，
  因此 bundle 行与纯名字行会归并到**同一身份**。
- 身份判定 `isNamedEntityTerm`：排除 `对象`/`身份` 子类、计数标签、`nkoma`/年代风格标签、
  纯符号与过短名称；`character` 分类本身不是身份证据。
- 解析结果 `PromptEntityResolution`：`resolved`（唯一身份，给出首选行 id 与显示名）、
  `ambiguous`（≥2 个身份，最多 5 个候选）、`unresolved`（名字原样保留）。
  `PromptRoutePlan` 决定 `lexical / hybrid / entity-only` 路径、是否允许创造和禁用类别。
- 纯身份/参数输入走 `entity-only`：跳过查询规划与检索（0 轮 0 查询），只组织固定身份与参数。
- 结果新增 `entityResolutions`、`routePlan`、`artistRoutes`，不新增 IPC 通道。结果区新增
  **“实体”** 标签：逐条显示提及、解析状态、身份 id、歧义候选，以及画师注入参数
  （管线、是否写入提示词、`artist_name`/`bank`/`style_guidance`/`adapter_strength`/底模）。
  条件栏新增 **“画师注入管线”**（跟随规则卡 / Anima / Kaloscope），只有非规则卡可推导的
  两条管线需要显式选择。
- 普通词守卫：不带引号、`@`、系列限定或中文的单个英文词，即使命中唯一角色名也不锚定身份
  （`dusk garden` 不再被当成明日方舟的 `dusk`）；多词名、`@`、引号、`name (series)` 与中文名
  仍然解析。歧义命中保持候选，不做唯一化。
- 7 份 locale 同步新增 `targetPipeline` / `pipelines` / `entityPanel` 文案；界面不含硬编码中文。

## 第六轮：工具化检索（模型做决策，2026-11-22，core 已落地）

### 为什么开发

前几轮的检索仍由程序先规划：润色是“先问模型要查询、程序检索、再让模型定稿”，扩写/专业/
反推则完全不经过动态检索。同一个词库因此有两套使用方式，模型也不能自己决定“再查一次”
或“这次不用词库”。本轮把检索变成模型可调用的工具，四种文本任务共用同一层。

### 两个工具

- `resolve_vocabulary({terms, category?})`：按用户原样写法做精确/别名解析，返回
  `resolved` / `ambiguous` / `unresolved`。`ambiguous` 只给候选，模型不得自行选择；
  身份结果不含外观，`hasAppearanceBundle` 仅作提示。`nsfw` 永不返回。
- `search_vocabulary({queries[]})`：每个槽位带 `slotId / category / query /
  alternateQuery? / purpose / depth / avoid?`，一次最多 4 个槽位。`avoid` 同时接受
  term id 与文本，跨调用去重由 Core 完成。artist/character/nsfw 直接拒绝并说明原因。

### 循环与 Core 的职责

- 真正的多轮：模型返回 `tool_calls` → Core 执行 → 以 `role:"tool"` 回填 →
  模型继续调用或给出最终 JSON。最多 4 个助手轮次、6 次工具调用；达到上限后
  下一轮强制 `tool_choice:"none"` 并记录警告，不静默截断。
- Core 只做预算、类别策略、冲突过滤、近重复折叠、跨调用去重和最终格式校验；
  “查不查、查几次、何时停”由模型决定。零调用、无匹配、整段不用词库都是合法结果。
- 预算沿用一个 `vocabularyTokenBudget`（默认 900），身份解析与检索共用；超预算返回
  `budget_exceeded`，模型可改用创造，不得重复同一查询刷预算。
- 最终答案必须同时给出 `initialPrompt / completePrompt / fields / termDecisions`；
  `termDecisions` 只允许引用实际返回过的 id，非法引用降级为创造并记警告。

### 接入方式

- `PromptOrchestratorLlm` 新增可选 `completeWithTools`；OpenAI 兼容实现发送
  `tools` + `tool_choice`，首条 user 消息携带参考图，后续轮次不重复发送图片。
- agent-led 下的扩写、专业、润色、反推（非 layout、非视频）统一走工具层；开启工具时
  关闭自动预选词，避免程序替模型“先答一半”。人工定稿、受控随机、Layout、视频保持原路径。
- 端点不支持 `tools` 或循环失败时，退回上一轮的路径（润色回动态润色，其余回静态选词），
  并在结果里写明“工具检索失败，已使用旧路径”，不把失败伪装成完整工具结果。

### 验证边界

- 已通过：`packages/core/tests/prompt-tool-retrieval.test.ts` 9 例（检索+身份两工具同轮、
  润色/反推共用、图片只发一次、禁查类别、avoid 与跨调用去重、预算耗尽、6 次调用后强制定稿、
  非法参数不中断会话、工具失败回退、零调用直出）；`prompt-orchestrator-llm.test.ts` 4 例
  （tools/tool_choice 请求体、assistant tool_calls 与 tool 回填、图片仅首条、截断拒绝）；
  既有实体路由 21、选词 14、动态润色 18 全部回归；四包 typecheck、`typecheck:tests`、lint 通过。
- **未验证**：真实本地/云端模型的工具调用兼容性（llama.cpp 需 `--jinja`；不兼容时只能观察到
  回退警告）、真实工具循环的端到端时延与 token 成本、界面策略对照在四模式下的实际观感、
  生图效果与 A/B/C。

## 第七轮：任务感知重排（2026-11-22，core 已落地）

### 为什么开发

到上一轮为止，候选只按“像不像”排序，模型看到的是一个混合池：完全等价的标签、更具体的
长短语、只是相邻的概念、甚至反义项都可能挤在同一组里。逆推需要“就是这个词”，扩写需要
“更具体一点”，润色需要“优先等价”，三种任务对同一批候选的取向不同，靠统一排序无法表达。

### 关系标签

检索层先给每个候选标一个与分数无关的关系：

| 标签 | 判定（确定性词法） |
| --- | --- |
| 等价 | 归一化文本相等，或词元集合相等 |
| 更窄 | 查询词元是候选词元的真子集（候选更具体） |
| 更宽 | 候选词元是查询词元的真子集（候选更笼统） |
| 相关 | 有词元交集，但互不包含 |
| 相反 | 否定词只出现在一侧，或命中内置反义对（soft/hard、day/night、亮/暗…） |

反义表刻意保持很小：它只负责挡住明显的反向项，不假装拥有语义理解。一个候选同时有
多个文本（en/zh/template）时取最强的正向关系；只有全部文本都指向相反时才判相反。

### 任务策略

- **逆推**：只接受等价，其他关系不进入候选，但在 `excludedRelations` 里留痕供审计。
- **扩写**：等价 +30、更窄 +12、相关 +2、更宽 −6；“更具体”是扩写想要的方向。
- **润色**：等价 +36、更窄 +6、更宽 −8；“等价优先”，但保留可用材料。
- **专业**：与扩写同一策略。
- 相反在四种任务里一律排除；受控随机与其他模式不加关系权重，保持原排序。
- 关系只加在既有词法分之上，精确命中奖励仍然主导；每个候选的 `relation` 随候选一起
  返回，两个工具与动态润色兜底共用同一实现。

### 91k 复测（同一隔离库、同一评测套件）

| 查询类 | B 面 @6（上一轮 → 本轮） | 顶部候选关系分布 |
| --- | --- | --- |
| 精确英文表达 | 28/28 → **28/28** | 等价 26、相关 2 |
| 中文片段 | 26/28 → **26/28** | 等价 20、更窄 7、相关 1 |
| 英文单词片段 | 17/22 → **17/22** | 等价 10、更窄 12 |

A 面 @6 同样未变（28 / 27 / 12）。结论：关系重排改变的是候选的解释与方向，没有改变本
样本的 top6 命中；单词片段的主要候选是“更窄”的长标签，说明缺口仍是可见度竞争，不是漏召回。
因此本轮继续不接 Embedding，也不做全库向量化；若后续仍要提升，应先做深度/预算的程序化
实验，而不是先上向量召回。

### 验证边界

- 已通过：`packages/core/tests/prompt-relation-rerank.test.ts` 7 例（五类关系、逆推只留
  等价并审计其余、扩写接受并偏好更窄、润色等价置顶、随机模式不过滤、工具返回关系与
  `excludedRelations`）；既有工具循环 9、实体路由 21、选词 14、动态润色 18 回归；
  真实 91k 评测 10 例全部通过，报告含关系分布。
- **未验证**：反义表只覆盖常见对，无法处理未列出的反义或隐喻；逆推“只接受等价”对长句
  可能返回空候选（属设计取舍）；真实模型看到关系标签后的选择行为、生图效果与 A/B/C 未测。

## 第八轮：全模式统一决策/溯源与结果级反馈（2026-11-22，已落地）

### 为什么开发

到第七轮为止，只有润色与工具模式会给出 `termDecisions`；“词条溯源”也只覆盖
`selectedTerms`，实体、画师注入和固定约束散落在不同标签页。用户换一个模式，就换一套
解释方式，无法横向比较“这次到底用了什么、为什么用、有没有真的进提示词”。同时结果只有
“存库/收藏”，没有任何“这次结果好不好”的记录，后续评估仍只能靠人肉记忆。

### 统一决策与溯源

- 结果新增始终存在的 `provenance`：每条词条、解析实体、画师路由和用户固定约束都有一行，
  字段为 `kind / state / outcome / excerpt / origin`。
  - 状态：锁定、推荐、参考、排除、自动、随机、已解析、待选择、未收录。
  - 结果：固定写入、复用、借鉴、未采用、参数注入（Kaloscope）。
  - 来源：用户、模型、规则。
- 模型给出决策时保留 `origin:"model"`；没有模型决策的模式（人工定稿、受控随机、Layout、
  视频、降级）由 Core 按用户状态与实际字段使用推导 `origin:"policy"` 的决策，
  因此“策略对照”在每个模式都有内容，且不会把规则推导冒充模型判断。
- 实体与画师并入溯源：解析出的身份对应固定字段则记“固定写入”，Kaloscope 注入记
  “参数注入”并给出去敏参数摘要；歧义/未收录保留原因，不伪造采用。
- 结果区“词条溯源”改为五列（状态 / 词条 / 结果 / 片段 / 来源），数据全部来自 Core，
  渲染层不再自行推断；默认标签只在存在模型决策时进入“策略对照”。

### 结果级反馈

- 结果区新增“结果反馈”：可用 / 不可用，可选原因（偏离意图、主体不对、太笼统、过度具体、
  元素冲突、风格不对、格式坏了、其他）与补充说明；提交后显示“已记录”。
- 新增 SQLite 表 `prompt_orchestration_feedback`（评分、原因、备注、输入/结果摘要与
  `snapshot_json`），索引按时间与评分建立；旧库通过 `migratePromptFeedback` 幂等补表。
- 快照只保存本次结果相关字段（completion、决策、溯源、检索摘要、警告、token 指标），
  **不保存参考图与 Layout 大对象**；不写 `prompt_terms`，不改变任何验证状态。
- 链路：React → preload `submitFeedback` → IPC `prompt:orchestrator:feedback` → main
  service 校验 → `PromptFeedbackDB` → SQLite；无新端口、无外部服务。

### 验证边界

- 已通过：`prompt-provenance.test.ts` 4 例（锁定/参考/排除的真实结果、实体固定字段、
  Kaloscope 注入、降级结果仍带溯源与规则决策）；`prompt-feedback.test.ts` 4 例（存取与排序、
  非法评分/原因/超长备注、空字节与空摘要、与词条验证解耦）；service 3 例（IPC 载荷校验、
  快照不含图片/Layout、随机模式摘要）；既有 77 例编排回归；四包 typecheck、
  `typecheck:tests`、lint、生产构建、i18n 冒烟与硬编码回归通过。
- 真实 Electron 点击验收：隔离 profile + 本地 mock OpenAI（工具调用→最终 JSON），
  策略对照显示“模型决策/复用”，词条溯源显示“自动/复用/soft light/规则”，
  结果反馈提交“可用 + 风格不对 + 备注”后写入一条记录；截图见
  `outputs/p4-decisions-provenance-feedback-20261122/`。数据库抽查：1 条记录，
  snapshot 含 `termDecisions`（model/reuse）与 1 条 `provenance`（policy/verbatim）。

## 第九轮：功能键耦合与结果回填（2026-11-22，已落地）

### 为什么开发

选材台的状态实际上已经在切换模式/规则卡时保留，但界面没有任何地方说明这一点，用户无法
确认“换了模式我的锁定还在不在”；同时结果里的词条只能看，不能一键回到选材台继续迭代，
每次都要重新搜索、重新定态。P5 把这两件事补成一个闭环。

### 跨模式共享

- 条件栏新增“跨模式共享”摘要：已选、锁定、排除、档案数量，并明确提示
  “切换模式或规则卡不会清空选中、锁定、排除与模型/LoRA 档案”。
- 共享范围：选材台的选中/锁定/参考/排除、`modelId` 与 `loraIds` 档案、系统提示词层。
  切换规则卡只改默认任务与输出格式，不动这些输入；切换模型来源也不清空选材。
- 这是对既有行为的可见化与回归约束，不是新增第二套状态：仍然只有一份 `prefabTerms`
  和一份档案字段。

### 结果回填选材台

- 结果区“完整改造”新增“回填选材台”：把本次结果的词条按溯源状态并回选材台。
  - 锁定→锁定；参考→参考；排除→排除；模型自动采用、随机、已解析身份、注入画师→推荐。
  - 自动选中但最终没进提示词的词条不回填，避免把模型淘汰的候选重新钉住；
    用户显式选择即使写入失败也会回填。
  - 已存在且处于锁定或排除的词条保持原状态，结果不能悄悄解锁或重新纳入；
    其余同 id 词条按结果状态更新，新增词条追加，不产生重复。
- 身份与画师行在结果里没有完整词条对象，回填时用 `vocabulary:resolve` 按标签
  （以及 `@标签`）找回存储行；找不到就跳过，不伪造词条。
- 回填是纯前端状态合并，不写数据库；完成后提示“已回填 N 条”，并把右侧面板切到选材台。

- 已通过：`prompt-backfill.test.ts` 4 例（新增/去重、锁定与排除不被覆盖、状态映射、
  自动未采用跳过而显式保留）；既有 77 例编排测试；四包 typecheck、`typecheck:tests`、
  lint、生产构建、i18n 冒烟与硬编码回归。
- 真实 Electron 点击验收：隔离 profile + 本地 mock OpenAI（工具调用→最终 JSON），
  回填后提示“已回填 1 条”，共享摘要“已选 1”；切到 Krea 2 再切人工定稿，选中保持；
  在选材台把词条设为锁定，再切回 MOSS，摘要仍为“已选 1 / 锁定 1”。截图见
  `outputs/p5-shared-selection-backfill-20261122/`。
- **未验证**：离开编排页再返回时，`prefabTerms` 仍随组件卸载丢失（当前不是持久化状态）；

## 第十轮：选材台与档案持久化（2026-11-23，已落地）

### 为什么开发

P5 让选中、锁定、排除和档案在模式切换时共享，但它们仍只存在于工作台组件内存里：离开
编排页、刷新或重启应用就全部丢失。用户需要的是“回来接着做”，而不是每次重新搜索定态。

### 存储与数据边界

- 新增 `prompt_orchestrator_state`（单行 `id='default'`，`state_json` + `updated_at`），
  旧库通过 `migratePromptOrchestratorState` 幂等补表；不引入新端口或外部服务。
- 只存工作集需要的字段：词条 id、分类、二级分类、中英文本、系列、模板、验证状态、
  选中状态（锁定/推荐/参考/排除），以及 `modelId`、`loraIds`。词条内容仍由
  `prompt_terms` 拥有，这里不复制验证结论，也不写回词条。
- 单行状态上限 4MB、词条上限 2,000 条；保存与读取都拒绝空字节。损坏的 JSON 行按空状态
  处理，下一次保存覆盖，不让工作台打不开。
- 该状态是本机工作区数据，不进入设置同步、备份或跨设备同步；需要时再单独评估。

### 加载与保存

- 工作台挂载时读取一次：合法行才恢复，未知状态/验证值按默认值降级，非法行跳过。
- 恢复完成前不写库，避免把初始空状态覆盖掉；恢复后对选中、`modelId`、`loraIds` 的变化
  做 400ms 防抖保存，输入模型 ID 不会逐键写盘。
- 清空选材台或清空档案同样会保存空状态，这是“用户确实清空了”的合法结果。

### 验证边界

- 已通过：`prompt-orchestrator-state.test.ts` 4 例（单行 upsert、重复 id 去重、非法状态/

- 结论：主进程事件循环没有被权重加载阻塞，“像卡死”来自缺少进度反馈和控件被禁用。
  因此没有引入 worker 线程或架构迁移，只补反馈与状态。

## 第二十五轮：知识分层与软引用（2026-11-25）

### 五层职责

- 规则卡：输出语法（caption / tags / layout），不承载知识。
- Skill：执行契约、流程、模式、输出格式；选包即整套生效。

  接口约定/串联/分工”归 contract；“色卡/导演风格/参考图”归 reference；其余 knowledge。
  “目标”仅整标题命中，避免误伤“人物目标”等知识。
