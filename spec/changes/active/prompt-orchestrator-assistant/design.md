# 提示词编排助手（PromptHub 内置能力）

## Product

Desktop

## 状态

review-pending — 第一版已实现并做针对性真实验证；第四轮原生 MOSS 布局画布已实现并验证，词条选材、风格/主题包和参考数据导入仍待实施与评审。

## 目的与定位

PromptHub 从"提示词管理工具"扩展为**知识驱动的提示词编排系统**。用户可以只给出
一句话意图，也可以主动挑选词条与预设；系统结合目标任务、规则卡片、风格/主题包
与创作偏好，从结构化词库精确选材，按视觉逻辑组织成更易被图像或视频模型正确执行
的提示词。底模与 LoRA 的搭配统计不属于当前范围，LoRA 仅在确有专用激活词时提供
可选约束。

**不是 RAG**：任务不是从文档找答案，而是选对元素并按目标组织。RAG 作为可插拔
后期模块，只承载社区经验、模型说明这类不适合拆成原子词条的内容。

**不做外挂**：不是独立 HTML 工具、不是本地插件、不是外部端口服务。是 PromptHub
自身的一等功能，落在既有包边界内：

- `packages/db`：结构化词库（已完成）
- `packages/core`：编排逻辑、技能规则、LLM 端口
- `apps/desktop`：IPC 入口与能力面板
- Skill 生成器：产出可复用的提示词技能，本地模型有参考但保留创造性

## 本地模型基线（2026-11-17 实测）

### 环境

- GPU：NVIDIA GeForce RTX 5060 Ti，8151 MiB 显存
- 内存：31.6 GB
- 引擎：llama.cpp build 12445（CUDA 13.5），`/d/tools/llama.cpp/llama-server.exe`
- 模型：`Qwen3.5-9B-The-Defiant-Fable-Uncnr-Heretic-NEO-MAX-IQ4_XS.gguf`
  （6.0 GB，**非 MTP 版**，见下节关键结论）
- 多模态：`...-MTP.mmproj-f16.gguf`（876 MB，视觉投影，尚未接入验证）
- 同机运行 ComfyUI（`krea2_image2.1_moss_minimax`），显存共享

### 速度实测（配置对照）

| 模型文件 | 配置 | 显存 | 生成速度 |
| --- | --- | --- | --- |
| MTP-IQ4_XS（6.1 GB） | ngl 99 / ctx 8192 / MTP 开 | 7680 MiB | 4.69 tok/s |
| MTP-IQ4_XS（6.1 GB） | ngl 99 / ctx 4096 / MTP 开 | 7631 MiB | 5.52 tok/s |
| MTP-IQ4_XS（6.1 GB） | ngl 28 / ctx 2048 / MTP 开 | 7630 MiB | 4.60 tok/s |
| MTP-IQ4_XS（6.1 GB） | ngl 99 / ctx 2048 / MTP 关 | 7630 MiB | 5.33 tok/s |
| **IQ4_XS（6.0 GB，非 MTP）** | **ngl 99 / ctx 4096 / 无投机** | **7355 MiB** | **60.09 tok/s** |

结论：

- **必须使用非 MTP 版本模型文件。** 同为 IQ4_XS 量化、同一引擎与硬件，
  MTP 变体只有 4.6–5.5 tok/s，标准版 60 tok/s，**相差约 11 倍**。
  MTP 变体多出的 `blk.32.nextn.*` 层被 llama.cpp 判为 unused 丢弃，但该文件
  在标准解码路径上无法获得有效 offload。带 `-MTP-` 的权重文件不要用于常规生成。
- 配置微调（层数、上下文、KV 量化、投机解码）对该差异无补偿作用，全部无效。
- 速度基线应记为 **约 60 tok/s**，早期 5 tok/s 的记录源于选错模型文件，已作废。
- 单次结构化编排实测：94 token / 2.1 秒 / 57.47 tok/s，交互完全可用。

### 关键运行约束

1. **必须关闭 thinking**：Qwen3.5 默认进入推理模式，`content` 返回空、
   内容全在 `reasoning_content`，80 token 全部消耗在思考链上。启动需 `-rea off`
   （或请求侧 `--reasoning-budget 0`）。
2. **与 ComfyUI 共享 8 GB 显存**：纯文本常驻约 7.3 GB，加载视觉投影后约 7.7 GB。
   生图前需卸载模型、生成后重载。该切换是必要项而非优化项。
3. **OpenAI 兼容端点可用**：`http://127.0.0.1:8080/v1/chat/completions`，
   PromptHub 无需理解 GGUF，按既有 openai 协议接入即可。
4. **视觉请求必须预留上下文**：单图默认占约 3800 token，`-c 4096` 时输出仅剩
   200 余 token，会在 `finish_reason: length` 处静默截断。识图场景 ctx 取 8192，
   并用 `--image-max-tokens 2048` 控制图片开销。

### 提示词遵从性验证

输入"东方女子倚在闺房窗边，黄昏，古典唯美写真"，要求输出结构化 JSON 并区分
fixed / flexible / optional 三层：

- 格式遵从：输出为纯净 JSON，无 Markdown 围栏、无前言、无解释。
- 分层正确：`fixed` 全部为用户明说元素；`flexible` 为黄昏光层次与空间关系
  推导；`optional` 为茶具蒸汽、钟声倒影等创意补充。
- 质量词抑制：未出现 masterpiece / 8k / ultra detailed 等无效词。
- 代价：94 token 耗时 2.1 秒（57.47 tok/s）。

**结论：模型完全可用。格式遵从、三层分层、质量词抑制三项均通过，单次编排
2–3 秒，可作为 PromptHub 的实时编排引擎，不需要为速度做交互降级。**

### 视觉能力验证（识图逆推）

`mmproj-f16` 视觉投影加载成功（`loaded multimodal model`），显存增加约 363 MiB。
测试图：动漫风格少女半身像（秋日欧式街道背景）。

识别结果与图片实际内容逐项一致：

- 发色发型：golden-blonde、两条粗麻花辫、黑色蝴蝶结缎带
- 服装：绿色水手领校服、白色条纹、大号黑蝴蝶结、米色格纹开衫
- 面部：琥珀色眼睛、泛红脸颊、嘴唇微张
- 动作：右手握住一缕发辫
- 场景与光照：虚化欧式街道、秋日树木、行人、明亮日光
- 风格：anime illustration

**关键可靠性证据**：模型主动输出 `not_visible: ["legs","feet","lower body"]`，
未对半身构图之外的部位编造内容。

图片 token 与质量的权衡（同一图片、同一提示词）：

| `--image-max-tokens` | prompt tokens | 总耗时 | 细节保留 |
| --- | --- | --- | --- |
| 默认（未限制） | 3799 | 约 80 秒 | 完整，含汗珠、手握发辫 |
| 1024 | 1223 | 约 24 秒 | 漏汗珠与手握发辫 |
| **2048（推荐）** | **2224** | **约 36 秒** | **含手握发辫、脸红、唇微张、黄格纹，仅漏汗珠** |

结论：识图逆推可用且不发散。**生产配置取 `--image-max-tokens 2048`**——
36 秒、细节接近完整，是速度与精度的最佳平衡点。1024 可作快速预览档。

## 第一版范围

不做 RAG、不建向量索引、不自动操作 ComfyUI（人工确认后执行）。

按顺序推进：

1. **词库维度补齐**（`packages/db`）：`series` 系列维度与长句模板位。
   现有 schema 只有 `en`/`zh` 两个短文本位，装不下社区词库的长句片段。
2. **编排层**（`packages/core`）：意图解析 → 词库选词（过滤适用模型、排除互斥）
   → 技能规则 → LLM 组合 → 三层输出（初始版／完整改造／分层字段）。
3. **任务、输出与适配分离**：扩写／专业／润色／反推／编辑／受控随机是任务；
   JSON 是输出结构，LoRA 是适配约束，都不再冒充普通任务模式。受控随机 = 先定场景
   约束再在范围内随机；底模/LoRA 搭配统计与自动注入模型 ID 不在当前范围。
4. **IPC 入口**（`apps/desktop`）：先可测命令，面板随后。
5. **Skill 生成器**：以词库与技能规则为参考，生成可复用的提示词技能文件，
   保留模型创造性，产出需标明哪些是参考、哪些是建议。
6. **本地模型设置与引擎控制**（用户后续明确要求）：设置内新增本地模型板块，
   管理 llama.cpp/GGUF/mmproj、推理参数、健康状态和自有进程启停；启动后连接现有
   AI 模型设置。编排工作台只提供状态、启动/停止和设置快捷入口。ComfyUI 的自动
   显存交接仍不在本轮范围。

## 第二轮：输入结构、官方规则与引导方式（2026-11-18）

用户实测反馈后，原生界面不再把八种模式视为同一输入，也不再继续平铺旧 `json/lora` 任务：

- 图片任务为扩写、专业编排、润色、反推、编辑、受控随机；JSON 改为可选结构化载荷，
  LoRA 改为高级适配约束。旧 CLI 的 `json/lora` 仍保留兼容，不用于新版界面分类。
- 反推支持文件选择、剪贴板粘贴和拖放；不同任务显示不同输入。每个任务旁直接展示
  用途、所需输入和输出，不要求用户猜测八种模式的关系。
- 引导方式分为 意图驱动 · 自动编排与词条驱动 · 人工定稿。词条驱动 · 人工定稿在右侧提供大面积词条选材
  搜索、分类筛选和显式锁定区，用户再补充一点想法，Agent 只做克制润色。
- 自动词库默认每类最多 2 条、约 900 Token 上下文预算；显式词条选材始终保留，
  词条驱动 · 人工定稿默认不自动加词。词库是按需知识，不是把整库复制给本地小模型。

### 官方资料的真实边界

- `prompt/moss官方生图规范.htm`：MOSS 支持 Caption、动漫 Tags、Layout JSON。
  新增 Tags 输出；长描述用普通英文句子，精确文字保留原语言与换行。
- `prompt/krea2官方生图规范.htm`：Krea 2 支持段落或短语列表，要求一种风格/媒介，
  保留原始主体、动作、数量、颜色、位置和媒介，不添加没有暗示的人物或物体。
- `prompt/minimaxh3官方生图规范.htm`：实际是视频规范，不是静态图规范。新增
  文生视频、首尾帧、多参、图生长视频、短剧 Agent 系统 Prompt 与实验性卡点任务。
  文生/首尾帧使用三字段，多参使用六字段；短剧产出的是 Agent 系统 Prompt，不是单条视频。
- Qwen Image 2.1 经用户确认本轮不接，不把 Krea 2 错写成 Qwen，也不编造其官方规则。

### MOSS Token 软预算与实体框架

用户确认的计数单位为 Token。`50–500` 收益明显、`500–2000` 收益递减、约 `2000`
较优、约 `2500` 进入平台期属于用户实测经验，不写成官方硬限制，也不强凑长度。
扩写可以深化初始框架中的神态、发型、服装、姿势、手部动作、场景内物件、材质、
光影与构图；避免突兀加入无关人物、动物或新剧情。结果优先调用连接模型的
`/tokenize`，不可用时给出确定性估算，并始终注明不是 MOSS/MiniMax 官方分词计数。

### H3 输入与验证

- 首尾帧重在撰写中间衔接，图片是可选参考，不调用 ComfyUI，也不假装已生成视频。
- 多参支持最多 6 张参考图和逐图用途；长视频要求连续性与总时长；短剧生成系统 Prompt。
- 卡点按用户时间戳组织切镜和动作重音，但明确标为实验性、待人工验证。
- Core 新增任务级输出校验：H3 缺三字段/六字段、短剧不是多段系统 Prompt、MOSS Layout
  不符合 summary/items/bbox 契约时，不能标记为完整结果，只能显式降级。
- 真实原生 E2E 已验证：剪贴板图片进入反推、H3 三字段真实生成、词条驱动 · 人工定稿搜索并锁定
  词条选材。另一次普通句子冒充 H3 的验收暴露问题后，已通过强化契约与校验修正。

## 第三轮：真实图片输入与规则隔离修正（2026-11-18）

- 本地图片不再依赖 Electron 原生文件对话框、复制到媒体目录和读回授权链，改为
  Chromium 文件选择后直接 `FileReader`，失败不再静默。
- Windows 系统剪贴板通过 Electron `clipboard.readImage()` 读取，同时兼容剪贴板中的
  本地图片路径。图片区显式处理 `Ctrl+V`，避免非编辑区域不触发 `paste` 事件；
  另保留“粘贴剪贴板图片”按钮与拖放。
- Token 区间只作观察指标，不用于提前结束、删减或强行凑齐。旧默认 `max_tokens=2048`
  已提高到 4096，避免 MOSS 正文加 JSON/字段后被提前截断；达到上限仍不采用半截正文。
- 选择顺序改为先选规则卡片，再显示该规则支持的任务：MiniMax-H3 只出现视频任务，
  MOSS/Krea 2 只出现图片任务。H3 不再显示 LoRA、图像系列和图片词条选材设置；
  Krea 2 只有 Caption，MOSS 保留 Caption/Tags/Layout。
- 结果区显示规则卡片与输出格式，视频结果使用“视频创意摘要 / MiniMax-H3 视频提示词”
  标题，不再与图片结果共用一套含混展示。
- 真实原生回归通过：实际 PNG 文件输入、系统剪贴板按钮粘贴、图片区 `Ctrl+V`，
  以及 MOSS Tags、Krea 2 Caption-only、H3 视频专属布局。

## 关键设计约束

- **三层创造力不可简化**：直接要求（必满足）／合理推导（可说明依据）／
  创意补充（必须标明是建议）。`moodyMossPromptWriting_v40.txt` 已内建
  FIXED / FLEXIBLE / OPTIONAL 三级标记，是该契约的既有实现，规则层不需重写，
  只需接入词库候选。
- **排序策略按模型可选**：kb.json 的 `semantic_order`（质量→画师→角色→外貌→
  服装→姿势→场景→光影→镜头）与 K2 协议要求（画风段必须最前且连续）不一致，
  不能硬编码单一顺序。
- **字段归属校验**：外观卡与写真包的既有实践已暴露真实冲突（"脚踝"属服饰而非
  标志特征；长卡只写身高体型比例，换景别才不矛盾）。词条需要分类归属约束与
  跨字段冲突检测。
- **角色档案与本次出图配置分离**：外观卡（跨场景稳定身份）对应角色档案，
  写真包（单次拍摄参数）对应本次配置，两者存储与生命周期不同。
- **验证状态不可省**：社区流传≠已验证；Krea2 有效≠MOSS 有效。词条需保留
  来源与验证状态（待整理／待验证／已验证／已弃用）。

## 对照式结果界面（2026-11-19 落地，已做真实模型复验）

- 布局由“上下堆叠”改为三栏：条件栏（规则卡/任务/模型/输出）｜工作区（输入、模式字段、词条驱动词库）｜结果栏（独立侧栏，可展开）。
  旧实现在 `xl`（1280px）断点以下退化为单列，左侧栏展开即触发，这是“看起来是上下”的直接原因。
- 结果栏内部为左右对照：左侧“原始要求”、右侧“生成结果”，逐句成行，便于横向比较。
- 句级关联采用确定性对齐（`packages/core/src/prompt-alignment.ts`）：先按标点切句，用字符二元组/词重叠做单调配对；
  若整段被改写导致重叠不足，则回退为按序配对。配对成功时点击右侧句子会加深左侧对应句。
  该对齐不依赖 LLM，避免模型错标；未能配对的结果句标记为“新增”。
- 系列：`listSeries()` 在词库无 `series` 元数据时回退为分类列表；按“系列”筛选词条时同时接受同名分类。
- 命名：原 `agent-led / human-led`（人弱引导/人强引导）改为“编排主导”下的
  **意图驱动 · 自动编排** 与 **词条驱动 · 人工定稿**，枚举值保持不变以兼容 CLI 与既有记录。
- 系统提示词层：新增 `systemPromptLayer` / `systemPromptLayerSource`。可从提示词库载入已保存 prompt 的
  `systemPrompt`，或直接手写；它作为附加系统指令进入组合阶段，不原样写入最终提示词，也不覆盖规则卡与用户固定事实。
- 存库/收藏：结果栏可“存入提示词库”，写入 `userPrompt=完整版`、`systemPrompt=系统提示词层`、
  `source=prompt-orchestrator`、`tags=[规则卡, 模式]`，并可选同时收藏；收藏走既有 `updatePrompt(isFavorite)`。
- 真实复验（本地 Qwen3.5-9B IQ4_XS，8080）：系统提示词层生效并体现在字段依据中；
  三句输入生成三组左右配对，点击右侧第 2 句时左侧“她的猫趴在窗台上。”加深高亮；
  存入后 SQLite 记录 `source=prompt-orchestrator`、`system_prompt` 与 `user_prompt` 正确、`is_favorite=1`。
- 仍未做：关系图谱联动、云端模型的供应商/端点展示、结果栏宽度拖拽记忆。

## 第四轮：词条选材工作台、风格主题包与原生海报布局（2026-11-19，布局画布已实施）

本节约束来自最新实测反馈。**原生 MOSS 布局画布已按本节后述契约落地并完成真实
Electron 验证；词条选材、风格/主题包和参考数据导入仍是已确认但未实施的需求。**

### 为什么继续开发

第一版已经证明“词库 → 规则卡片 → 本地或云端模型 → 对照结果 → 存库/收藏”的原生
链路可行，但当前词条选择密度、风格覆盖和窗口适应性仍不足：普通窗口下主按钮会被
挤成两行，词条选材区可选项有限，结果更像通用编排器而不是可精细控制的创作工作台。
下一阶段的目标不是复制一个独立提示词生成器，而是把丰富的选材、预设和布局能力
接回 PromptHub 已有的提示词库、收藏、系统提示词层与后续测试链路。

### 继承且不可回退的原则

- 所有新能力继续是 PromptHub 原生 Electron 功能，不引入独立 HTML、ComfyUI 插件、
  外挂应用或额外服务端口。
- 规则卡片决定模型语法与任务边界；风格包、主题包、词条和预设只提供创作素材，
  不得把 MOSS、Krea 2、MiniMax-H3 重新混成同一套输入和输出。
- 保留“直接要求 / 合理推导 / 创意建议”三层来源。用户显式选择的词条是直接要求，
  Agent 不得擅自替换；自动补充必须可识别、可审阅。
- Token 只作观察指标，允许合理冗余，不得为了落入区间而删减、提前结束或截断句子。
  词库上下文预算只限制注入小模型的参考资料量，不限制最终提示词长度。
- 词库是按需检索与组装的知识，不是把整库或整套模板一次性塞给模型。本地与云端
  chat 模型继续复用现有 AI 设置，不因增加选材功能而新建第二套模型配置。
- 结果继续放在右侧独立区域并保持左右句级对照；系统提示词层、存入提示词库和收藏
  是既有主链路，不能被新的选材界面削弱。

### 命名与普通窗口布局

- 界面新名称为 **“词条选材”**，替代“词库预制菜”。“词条驱动 · 人工定稿”继续表示
  先选材、后由 Agent 克制组织与润色的工作方式；内部枚举和旧数据无需改名。
- “开始编排”是主操作，不得因普通窗口宽度不足而压缩成两行。待实施布局将其放在
  中间工作区底部的完整宽度主操作区，保持单行、可见且不被右侧结果栏挤压。
- 宽屏保留“条件栏｜工作区｜右侧结果栏”。普通窗口优先折叠条件栏或把结果栏改为
  可展开右侧抽屉，为选材与主按钮让位；不得简单退化为上下对照。窄窗口也须保留
  明确的左右对照查看入口。
- 选材密度提高后，分类导航、候选区和已选区应分区滚动，不能让整页随词库长度无限
  增长；主要操作与已选摘要保持可见。

### 词条选材工作台

参考图 2 的多字段池交互以及两份本地工具的内容组织，待实现以下原生工作台：

1. **风格/媒介维度**：至少为写实、3D、2.5D、动漫预留独立素材包；它们不是新的
   规则卡片。动漫素材包可包含可选画师及画师相关词组，未选择时不得自动强加画师。
2. **多字段候选池**：按主题、人物、动作、动作细节、服饰、配饰、场景、光影、镜头、
   构图等字段提供搜索、分类、系列与候选列表。字段可声明单选、多选或每套取一条等
   选择语义，不再只有一个搜索框和少量候选。
3. **已选与约束**：已选词条形成可审阅清单，支持移除、排序、锁定、排除与随机时保留
   已选项；长句模板与短标签都是候选素材，但输出语法由当前规则卡片决定。
4. **预设与自定义组合**：可载入整组预设，也可只借用其中部分字段再调整。预设是可选
   起点，不是必须整套复用的固定模板。
5. **Agent 的后置作用**：在用户选材后做去重、冲突检查、字段归属、语法组织与克制
   优化；在“词条驱动 · 人工定稿”下不自动堆满其他分类，在“意图驱动 · 自动编排”下
   才允许按意图补充并标为合理推导或创意建议。
6. **模型差异**：同一动漫标签可作为 MOSS Tags 的候选，也能经 Agent 转写为 Krea 2
   自然语言 Caption 的素材；不得把标签串未经组织就当成所有模型的统一最终输出。

### 参考数据的导入边界

已只读核对以下本地资料：

- `prompt/提示词生成器v3.0/提示词生成器v3.0`：使用说明记录约 2467 条中英标签、
  32 个分类、507 个角色和 26 个预设；HTML 中还包含字段分类、语义排序和预设组合。
- `prompt/SkyLoongAI绘画工具集-精简版v2.1/SkyLoongAI绘画工具集-精简版`：`taglib.json`
  记录 15 个大类、167 个子类、7617 个标签，另有大型画师表与中英映射。原始自动翻译
  存在明显错译，不能因为数量大就直接视为已验证知识。

后续实现应通过版本化导入器把**审核后的**标签、分类、角色与预设转换为现有
`prompt_terms` / 关系数据，保留 `en/zh/category/series/template/source/validation`
及来源映射，并处理重名、同义词、下划线、转义括号和重复导入幂等。首批以动漫素材
为主，写实与写真素材后续单独整理。导入器可以读取这些本地文件，但运行时不得加载
参考项目的 HTML、EXE、代理、localStorage 或新增端口；本次没有执行批量迁移，也没有
把原始参考目录视为产品源码。

### MOSS 电商/海报主题与原生布局编辑

- 电商、海报等主题素材包仍待实施。主题包将提供构图候选、文案区、主体区、装饰区和
  常用预设；预设布局与 Agent 建议布局都必须进入同一个可视化确认步骤。
- 海报布局参考 [ComfyUI 官方 MOSS-Image 教程](https://docs.comfy.org/tutorials/image/moss-image/moss-image)
  中 `Create Bounding Boxes` 与 `MOSS-Image Layout Prompt` 的语义，但实现位置是
  PromptHub 编排助手自身，不安装 ComfyUI 节点或插件。
- **原生编辑器已实现**：1:1、2:3、3:2、4:3、3:4、16:9、9:16、21:9、9:21
  九种精确比例与自定义 16 倍数尺寸；10×10 相对网格；
  空白拖框、添加、移动、右下角缩放、删除和顺序调整；逐框视觉描述；`object/text`
  类型；精确多行文字；角色框标记；0–1000 归一化坐标微调。切换比例保留相对布局。
- **Core 确定性编译已实现**：编辑器保存 normalized `yxyx`，最外/最小边向下取整、
  最大边向上取整后减去画布半宽/半高，生成 `summary/items/abs_centralized/yxyx` 模型
  JSON。画布、尺寸、框数量、ID、文本、坐标范围与顺序均在边界校验；角色框以 1 起始
  序号单独输出为 `characterBoxes`，不向模型 JSON 添加非标准字段。
- LLM 只优化整体 `summary.caption` 与逐框 `caption`，不得修改坐标、框顺序、类型或
  精确文字。初始和编排后 JSON 均由 core 编译；LLM 失败时返回明确 degraded 的有效
  Layout，不接受半截 JSON。Layout 不得再被下游提示词增强器改写；本阶段仍只生成
  提示词与布局，不自动操作 ComfyUI 或生成图片。

### 逐框描述可留空与海报布局反推（2026-11-19 追加）

- 逐框视觉描述不再作为编排前置阻塞条件：留空的框由编排助手按整体意图补齐，已写的
  描述会被润色；精确文字（文本框 `text`）仍是硬要求，坐标、框顺序、类型和精确文字
  在补齐/润色过程中由 core 保护，模型不得改写。
- 新增两个原生能力，均为 `renderer → preload → main IPC → core → 已配置 chat 模型`：
  - **补齐/润色逐框描述**：只返回逐框描述数组；模型失败时保留用户原值并标记
    `degraded`，绝不填充编造内容。
  - **从海报反推布局**：多模态模型返回 `summary + boxes`，坐标归一化为 0–1000
    `yxyx`，按绘制顺序排列（背景→主体→文字）。识别出的精确文字可编辑；含不确定
    字符的文字框标记 `needsReview`（画布显示“待核对”角标），避免把 OCR 猜测当成
    既定事实。无法识别或全部框非法时返回空草稿与原因，不覆盖现有画布。
- 反推结果写入同一 `PromptMossLayoutDraft`，因此可直接继续拖动、改文案、跑编排、
  存库；不会引入新端口、新插件或独立页面。
- 上述两项已通过 core 单测（8/8，含坏 JSON、坐标越界、0–1 浮点缩放、`?` 不确定
  文字标记）与 Desktop 构建验证。**尚未做真实多模态海报反推的画面质量验收**，
  因此整体状态保持 `review-pending`。

### 已保存提示词拆解的归属

用户认可并已保存到 PromptHub 的提示词，可以在后续由独立功能拆解为预设、字段片段
或新词条，并保留来源 Prompt 关联与人工确认。这属于**提示词库知识沉淀/词库维护**
的独立开发主题，不在本轮编排助手直接实施，也不得在用户不知情时自动污染全局词库。

### 第四轮验收边界

剩余实施至少验证：普通窗口主按钮始终单行可用；选材后三层来源不丢失；风格包不改变
规则卡片输出契约；参考数据导入可重复且不重复造词。MOSS 海报框选、程序校验 Layout
及存库已经完成下述针对性验证，但其他第四轮功能未因此关闭，状态保持 `review-pending`。

### 原生布局画布验证证据（2026-11-19）

- `packages/core/tests/prompt-moss-layout.test.ts`：5/5，通过归一化坐标、16:9 重缩放、

- 临时真实 Electron E2E 使用隔离 SQLite 与测试进程内模拟 OpenAI 响应，完整通过：
  空白拖框、对象/文字框、角色标记、移动和缩放坐标变化、16:9 切换、IPC 编排、右侧
  初始/最终 JSON、精确多行文字、像素 bbox 以及 `source=prompt-orchestrator` 存库和

## 评估方式

A/B/C 三版对比：A 原始输入、B 普通大模型扩写、C 编排结果。固定底模、LoRA、
采样器、步数、CFG、分辨率、种子，按意图保留、主体准确、构图准确、细节质量、
风格一致、冲突程度、冗余程度七项分评。比较同等成本下的结果质量，不比较长度。
